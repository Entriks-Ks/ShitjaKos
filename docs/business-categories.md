# Business categories

Business categories describe the shop, separately from categories/attributes on its listings.
Owners choose one active top-level SHITJAKOS category and up to three additional distinct categories. Position zero is primary. All selections are validated and replaced in the business transaction; workers cannot edit them. Category use prevents hard deletion; archiving retains the relation but excludes it from public filters/labels. Owners see an unavailable-category notice when editing.

Existing businesses are not assigned guessed categories and remain in unfiltered shop results. Creation now requires categoryIds. Partial updates may omit categoryIds to preserve current selections. Sending an empty list is invalid.

Web: business form -> action -> business service -> repository. Shop directory filters category and city using GET parameters and displays category chips; detail pages display the same categories. This adds dropdown filtering, not text search by shop name. Inventory categories remain independent.

Mobile:
- POST /api/v1/businesses JSON includes categoryIds: [primaryId, ...additionalIds].
- Multipart POST repeats categoryIds for every ID (primary first), including when uploading images.
- PATCH /api/v1/businesses/{id} accepts the same array.
- GET /api/v1/businesses/{id} and membership lists include ordered business.categories for editing.
- GET /api/v1/categories supplies catalogue options; select active entries with parentId=null and ownerPortal=SHITJAKOS.
- GET /api/v1/shops?category=CATEGORY_ID&city=Prishtina&page=1&limit=20 applies both filters.
- Public shop list/detail include only active selected categories with translations.
The existing mobile UI must send categoryIds on new business creation; older clients omitting it receive validation errors. No native app source was changed here.

The applied 20261013140948 migration also dropped four custom trigram indexes. The follow-up 20261013150000_restore_search_indexes recreates them without changing the applied migration history. Future autogenerated migrations should be reviewed for unintended removal of these custom indexes.
